# CowBot 0.1.5 — Agent direct conversations

CowBot 0.1.5 makes talking to an agent the first thing the desktop does. Until
now an agent answered only when a channel message mentioned it, so reaching one
agent meant a shared room and mention syntax. Every agent now has a direct
conversation, and the shell is organized around agents rather than channels.

## Highlights

- **Message an agent directly.** Every agent has exactly one direct
  conversation. Open it from the contact list and every message you send reaches
  that agent — no mention required. A direct conversation has a single
  addressee: `@team` does not fan out, and a mention of another agent is plain
  text. See
  [ADR-0024](https://github.com/BerryUIKI/CowBot/blob/main/docs/ADR/0024-agent-direct-conversations.md).
- **A conversation-first shell.** The sidebar now starts with searchable agent
  contacts, each row showing an avatar, the latest-message preview, and a time,
  ordered by recent activity. Group channels sit below them in their own
  section. The main pane is a chat thread — user bubbles on the right, agent
  bubbles on the left, system notices centered, and a typing bubble while a
  turn runs — with a floating composer. Tasks, Approvals, and Settings move to
  the sidebar footer; Tasks keeps its list in the sidebar and its detail in the
  main pane.
- **Group channels keep the 0.1.4 behavior.** A group channel still answers
  `@Agent` and `@team` mentions, still posts notices for unknown mentions and
  failures, and keeps its per-channel approval policy. Direct conversations and
  group rooms share the same scheduler, approval gate, run history, and event
  stream.
- **Existing workspaces gain conversations automatically.** Migration 0003 adds
  `channels.agent_id` and a partial unique index on `(workspace_id, agent_id)`,
  so "one conversation per agent" is a database invariant. Conversations are
  provisioned idempotently at startup, after onboarding, and after a template
  adds agents, so existing workspaces and imported packages gain a conversation
  for every agent without a data migration step.
- **`.cowpkg` packages stay compatible.** `channels.jsonl` gains an optional
  `agent_id` field; packages written before this release still import because
  the field defaults to `null`.
- **Old migration checksums repair themselves.** A local database created by an
  earlier Windows build could record migration checksums for CRLF line endings
  and then fail to open with `migration 1 was previously applied but has been
  modified`. `cowbot-store` now accepts a checksum only when it matches the
  current migration SQL with either line ending, verifies the live schema
  against a fresh application of the embedded migrations, and then updates only
  the checksum column in one transaction. When the schema does not match, it
  leaves the database untouched and reports recovery steps.
  `.gitattributes` pins migration files to LF.
  See
  [ADR-0025](https://github.com/BerryUIKI/CowBot/blob/main/docs/ADR/0025-database-migration-checksum-compatibility.md).
- **Documentation.** New ADRs 0024–0025, an architecture update for owned
  channels, a package-format note on `agent_id`, and new user-guide sections on
  direct conversations and the repair notice.

## Upgrade

- **Windows (NSIS setup):** updates in-app from 0.1.4.
- **Windows (MSI):** install the new NSIS setup or MSI manually.
- **macOS (from the DMG):** updates in-app. Builds remain unsigned and
  un-notarized, so macOS may ask you to allow CowBot again after an update.
- **Linux (AppImage):** updates in-app.
- **Linux (deb):** download and install the new package.

Existing local databases, `config.json` files, and `.cowpkg` packages from
0.1.4 continue to work. Migration 0003 applies automatically on first launch
and creates a direct conversation for each agent in the workspace.

A database that an earlier Windows build stamped with CRLF migration checksums
is repaired automatically after schema validation; its rows are preserved. Back
up the workspace database with its `-wal`/`-shm` sidecars before the first
launch if you want a safety copy. Once 0.1.5 opens a database, migration 0003
is recorded, so an older build (0.1.4 and earlier) reports it as a missing
migration and refuses to open that database; restore the backup to go back.

With no active provider the desktop still falls back to the offline mock model,
so a direct reply reads as an echo; a provider that is configured but cannot
answer posts a system notice with the model error instead of staying silent.

## Known limitations

- Local/offline single-user mode only: no server, remote sessions, or
  multi-user workspaces.
- Each agent has one direct conversation, and it cannot be renamed or deleted
  from the UI. There are no unread counts, attachments, streaming answers, or
  multi-user direct messages, and agents cannot be deleted yet.
- Group channel answers are one turn per mentioned agent. A reply uses the
  channel's recent history rather than a thread, and agents never answer an
  unmentioned message in a group channel.
- Sequential Planner → Coder → Reviewer crews; no hierarchical orchestration,
  DAG workflows, or agent-facing delegation tool.
- No streaming responses, retries, rate limiting, or token accounting.
- The subprocess sandbox is not OS-level isolation.
- Builds are unsigned; updater signatures are separate from code signing.
- Workspace deletion and renaming are not available in the desktop UI.

# CowBot 0.1.17 — Agents you can talk to from your team's chat

CowBot 0.1.17 adds the integration workstream: a CowBot channel can now be bound
to a conversation on Mattermost, Telegram, Slack, or Feishu, and an agent answers
there. Somebody mentions the bot in a group, or messages it directly, and the
answer appears in that chat with no CowBot window open — the server runs the turn
itself.

Four platforms ship, and **all four dial out**. Mattermost and Slack open a
WebSocket, Telegram long-polls, Feishu runs its long connection. A deployment
needs no public URL, no reverse proxy, and no TLS certificate in front of CowBot
for any of them, which is what makes a bot possible for a team that already runs
a server but not an ingress.

A database migration ships: schema version 21 adds four tables for integrations,
bindings, provisioned accounts, and deduplication. They are additive, so a
0.1.16 workspace upgrades in place and an integration-free workspace behaves
exactly as before.

## Changes

- **Four IM platforms.** **Settings → Integrations** creates a bot from a
  platform, a label, and its configuration, then binds an external conversation
  to a CowBot channel. The configuration is sent once and never returned — not by
  any read, not in a log line, not in a `.cowpkg`. A binding can name one agent,
  which is how a mention of the bot becomes an `@Agent` turn in a group channel.

- **No inbound surface by default.** Each adapter connects outward, so the
  requirements are a bot token and nothing else. Feishu's long connection means
  no Encrypt Key and no signature either, and Slack's Socket Mode means no
  signing secret: there is no inbound request to verify.

- **A webhook transport when dialling out is not possible.** Each platform also
  accepts deliveries at `POST /api/v1/integrations/{id}/webhook`, for a
  deployment behind an ingress or on a container platform that scales to zero.
  Choosing it trades the dialect for a public hostname and TLS. Verification is
  per platform — an HMAC for Slack, a secret header for Telegram, AES-256-CBC
  plus two signature schemes for Feishu — and runs over the raw body before
  anything parses it.

- **Approvals happen in the chat.** An agent that needs a tool approved asks in
  the IM: an inline keyboard on Telegram, a Block Kit message on Slack, an
  interactive card on Feishu, and a reply prompt on Mattermost. **Only the person
  who asked and a workspace administrator may answer** — every role can write and
  a card sits in a shared room, so without that check anyone present could
  approve somebody else's code execution. The card is revised once decided, and
  the decision is attributed to the IM account, not the bot.

- **Files sent in the chat reach the agent.** An attachment is written below the
  server's tool root and its path is appended to the message text, so an agent
  reads a CSV or a log with `read_file` and inspects anything else with
  `execute_code`. The stored name is generated rather than the sender's, the size
  is capped at 20 MB while the bytes arrive, and the download happens only after
  the delivery is claimed, so a platform retry fetches nothing. **A model in this
  build cannot be sent an image**, so a photo is stored and named, not
  understood.

- **A binding that cannot receive says so.** Every platform has a requirement a
  binding row cannot express — the bot must be invited, added, or made an
  administrator — and failing it is silent rather than broken. Bindings are
  checked when created, and at startup a problem posts a notice into the CowBot
  channel it points at. A check that could not run reads as "unknown", never as
  healthy.

- **IM accounts become workspace members.** The first message from a platform
  account provisions a CowBot user with no password, so it can never sign in but
  does appear in the timeline and the audit trail.

## What does not change

CowBot is still local-first, and no integration runs in the desktop app.
Integrations are a server feature: they start at boot when the server has a model
provider configured, and they are configured by a workspace administrator.

## Upgrade

- **Windows (NSIS setup):** updates in-app from 0.1.16.
- **Windows (MSI):** install the new NSIS setup or MSI manually.
- **macOS (from the DMG):** updates in-app. Builds remain unsigned and
  un-notarized, so macOS may ask you to allow CowBot again after an update.
- **Linux (AppImage):** updates in-app.
- **Linux (deb):** download and install the new package.

The migration is additive, so a 0.1.16 database upgrades in place and a workspace
with no integrations has no new rows. Integrations are deployment state and are
never exported in a package, so importing a workspace does not carry a bot token
with it.

## Known limitations

- **Images are stored and named, not understood.** The LLM layer carries text in
  every protocol, so a photo is a file path rather than a picture. Text files,
  CSV, JSON, and logs do reach the agent.
- **One process per Slack or Feishu app.** Both platforms deliver each event to
  one connection, so two servers on the same app token each see a subset.
- **An answer is never sent back as a file.** The agent's reply is text; there is
  no rule for which of the files a turn wrote is the deliverable.
- **The webhook transports are not tested against the live platforms.** Signing
  and decryption are covered by unit tests, a published AES test vector, and
  route tests; a deployment is the first place a real platform's signature is
  checked end to end.
- **A bot removed from a chat after startup is noticed at the next restart.**

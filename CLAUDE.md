# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository Overview

CowBot is an open-source, high-performance multi-agent collaboration platform with code execution and automation capabilities, built in Rust. It utilizes an event-driven message bus for decoupled multi-agent communication and modular tool sandboxing.

## Git Workflow (GitFlow)

- **Strict rule**: NEVER push directly to `dev` or `main`. Both branches have GitHub branch protection enabled with pull request requirements and force-push/deletion blocked.
- `main` — release-ready history only; protected.
- `dev` — integration branch for completed features; protected. All feature pull requests must target `dev`.
- `feature/<name>` — branched from `dev`, pushed to origin, and merged into `dev` via Pull Request (`gh pr create --base dev`).
- `release/<version>` — branched from `dev` when preparing a release, merged into both `main` and `dev` via Pull Request.
- `hotfix/<name>` — branched from `main` for urgent fixes, merged into both `main` and `dev` via Pull Request.
- Commit messages are small, atomic, and English; always use PRs to merge into `dev`.

## Workspace Architecture

The project is structured as a Cargo workspace under `crates/`:

- **`crates/cowbot-core`**: Core domain types and shared errors (`CowError`). Defines `AgentProfile`, `Task`, `Channel`/`ChannelMessage` (a channel with `agent_id` is that agent's direct conversation, ADR-0024; `pinned` records user pinning, ADR-0026; `kind` distinguishes group channels, direct conversations, and user-created conversations, ADR-0030), conversation sessions with settings (including the model scope, ADR-0049), ordered participants, append-only `ContextEntry` branches with optional peer authorship, context events, projection, and compaction helpers (ADR-0030, ADR-0032), routing sources (mention, router, rotation, default), routing modes, group reply cleanup, and group turn records, notes and memory entries with four scopes, statuses, sources, budgets, deterministic ranking and selection, notes rendering, and deterministic credential redaction (ADR-0033), task run groups, task sources that separate user work items from channel and conversation turns, and git worktree lifecycle types (ADR-0031), `@mention` parsing and resolution (ADR-0022), the `Tool` trait, the `Event`/`EventPayload` bus message model (including assignment, worktree, and conversation-routing events, ADR-0031, ADR-0032), and normalized LLM token-usage types, the `TokenCounter` contract with its source and label, and a character-based estimator used as the fallback (ADR-0029, ADR-0035), plus read-only `PromptPlan` values with named prompt slots, message costs, tool schemas, and recall candidates with skip reasons for the context inspector (ADR-0036), and sealed `LlmPromptSnapshot` documents with ordered messages, tool-call arguments, prompt slots, the memory selection, a token count, a content hash, and workspace retention settings (ADR-0037). `/btw` side questions, which run one agent turn through `execute_messages` and return the answer for an ephemeral panel while writing no message, context entry, or routing turn, recorded as `LlmCallKind::SideQuestion` (ADR-0039). A static slash command catalogue with a pure parser — names, aliases, usage, summaries, argument specs, and a `Chat`/`Conversation` target — shared by the desktop, the CLI, and future remote clients (ADR-0038). The turn contract: a `TurnId`, the `TurnEvent` lifecycle (started, text and reasoning deltas, tool start and finish, approval required, done, error), a `TurnControl` the runner implements, and the `CancelSignal` cancellation primitive with wakeups, all shared by chat, group, channel, and task turns (ADR-0041).
- **`crates/cowbot-bus`**: Tokio broadcast-backed `EventBus` with subscriber handles and a bounded in-memory event history.
- **`crates/cowbot-tools`**: `ToolRegistry` plus the built-in tools (`CodeExecutionTool`, `ReadFileTool`, `WriteFileTool`), the pluggable `SandboxBackend` trait implemented by `SubprocessSandbox`, and the deterministic `StaticRiskClassifier`.
- **`crates/cowbot-llm`**: `LlmProvider` abstraction with an OpenAI Chat Completions client (works with OpenAI, DeepSeek, Ollama, etc.), an Anthropic Messages client (Claude and Claude Code-compatible relays), an OpenAI Responses client (Codex-style endpoints), and a `MockLlmProvider` for offline tests and dry runs. `chat_stream` streams normalized text, reasoning, tool-call, and usage chunks with cooperative cancellation through a shared `CancelSignal`, over a common SSE decoder, and a default adapter keeps non-streaming providers working (ADR-0041). A model-to-tokenizer map counts `o200k_base` and `cl100k_base` OpenAI-compatible models exactly with compiled-in vocabularies, and returns the character estimator for every other model (ADR-0035). Responses carry normalized token usage, including DeepSeek cache hit/miss fields, and preserve the provider's raw usage object. `LlmProvider::list_models` queries each protocol's model catalogue for the desktop's Fetch models action (ADR-0021) and returns a `DiscoveredModel` per entry — the id plus the context window and output limit the endpoint advertises, read from `context_length`/`max_input_tokens`/`context_window`/`context_windows` and `max_output_tokens`/`max_completion_tokens`, with either left `None` when the endpoint is silent (ADR-0029).
- **`crates/cowbot-agent`**: Agent runtime loop (LLM call → tool calls → observations), an optional `ToolGate` consulted before each tool execution, an optional `LlmUsageRecorder` invoked after every completion, an optional `ConversationRecorder` that mirrors assistant/tool messages into a conversation branch, `execute_messages` for caller-assembled requests (ADR-0030), streaming through a `TurnObserver` that reports text and reasoning deltas and tool start/finish, a running partial draft that survives stops and failures, sequential `Crew` orchestration, and preset roles in `StandardRoles` (Planner, Coder, Reviewer).
- **`crates/cowbot-store`**: SQLite persistence built on `sqlx`: embedded migrations, connection management, and repository methods for identity, collaboration, agents/templates, tasks (including run groups and sources)/assignments/runs/tool calls/LLM calls/approvals, task worktree records (ADR-0031), conversation settings with the model scope and default responder, participants with roster positions, context entries with peer authorship, context events, and device-local group turn records (ADR-0030, ADR-0032), notes, memory entries with an FTS5 trigram index maintained by triggers (insert/update/delete, including cascades), filtered entry listing, pinned and scope-aware recall search with a LIKE fallback, recall statistics, and workspace memory settings (ADR-0033). Each run persists the executing agent profile snapshot, so transient crew roles keep an identity for previews and audit (ADR-0036). `upsert_agent` never reassigns `workspace_id`, so an agent id offered to the wrong workspace writes nothing and reports `false` instead of moving the row. Prompt snapshot rows are keyed by their LLM call, cascade with it, carry their workspace for scoped retention, are verified against their content hash on read, and are deleted by age or by channel without touching usage rows (ADR-0037).
- **`crates/cowbot-mattermost`**: The first platform adapter (ADR-0057). `config.rs` reads the two values an operator stores (`base_url`, `bot_token`) and derives the socket URL; a `wss://` base is refused because that URL is derived. `rest.rs` calls `users/me`, `config/client` (for `MaxPostSize`), `users/{id}`, and `posts`; its `Debug` prints no token. `socket.rs` runs the WebSocket, whose auth is *in-band*: the token is the first frame and a `status` event is the readiness signal, so a connect is not done when the handshake completes and a `status: FAIL` is an error naming the token rather than a retry loop. `adapter.rs` translates: a `posted` event nests its post as a JSON string, a thread is a `root_id`, a bot username ends in ` [bot]`, and only the bot's own mention becomes `@AgentName`. Addressing means a mention of the bot, so every post in the channel is stored but only a mention starts a turn. Identity and the post limit are discovered at startup, not configured. `Integration::check_binding` (default `BindingHealth::Unknown`, never `Reachable`) lets an adapter say whether a bound conversation can actually reach it; Mattermost answers from `GET /channels/{id}/members/{user}`, since it delivers posts only for channels the bot has joined and a binding that misses one is silent rather than broken. It is asked on bind, in the response, and at startup, where a problem posts a notice into the CowBot channel it points at. The server starts integrations from `integration_startup.rs` at boot, and only when a model provider is configured.
- **`crates/cowbot-telegram`**: The second platform adapter and the first SaaS one (ADR-0058). `config.rs` reads the one value an operator stores (`bot_token`, refused unless it is shaped `<digits>:<secret>`, with a message naming BotFather) plus an optional `api_base` for a self-hosted Bot API server. `update.rs` models the update envelope and, more importantly, gets Telegram's text protocol right: entity `offset`/`length` are **UTF-16 code units**, so an emoji before a mention shifts every later offset, and `slice_utf16` converts while an offset inside a surrogate pair returns `None` rather than panicking. A message addresses the bot through a `mention` of its handle, a `text_mention` whose `user.id` is the bot's, a reply to one of its messages, or a `/command` that carries no `@handle` — `/help@other_bot` is that bot's command. A private chat is addressed by definition, which is CowBot's direct-conversation mode; in a group, Telegram's default privacy mode delivers only what addresses the bot, which is ADR-0022's mention turn. `api.rs` is the Bot API: `getMe`, `getUpdates` (asking only for `message`, and confirming a batch by advancing the offset), `sendMessage`, `getChat`, `getChatMember`, over a shared envelope whose poll timeout is longer than the long-poll deadline it asks for. A `409` (a webhook is set, or another process polls) and a `401` are terminal and name the fix; a `429` waits exactly the `retry_after`; everything else backs off from one second to a minute. `render.rs` converts an agent's Markdown to Telegram's HTML — escaping first and adding tags after, so a `<b>` in a code block stays code — and the adapter falls back to plain text when Telegram still refuses the markup, because an unformatted answer beats a lost one. `adapter.rs` ties it to the pipeline, refuses a token that belongs to a person rather than a bot, and implements `check_binding` from `getChat` (a `400 chat not found` and a `403` are facts about the binding; a `401` or a `5xx` is `Unknown`, never `Unreachable`) plus `getChatMember` for a channel, where being present is not enough and posting needs administrator rights. It reports `ChunkLimit::Units(4_096)` through `Integration::chunk_limit`, so the mirror splits its answers in the unit Telegram measures.
- **`crates/cowbot-client`**: Transport-neutral `Client` trait, the local-mode `LocalClient`, and the server-mode `RemoteClient` (ADR-0045, ADR-0053), which opens SQLite, bootstraps the local workspace, runs startup reconciliation, and exposes session, channel/message and channel-management operations (rename, pin, delete, clear history), conversation creation from a `NewConversation` value (single or ordered group participants), conversation summaries with participant profiles, participants, routing turns, settings, context projection, per-participant clearing and compaction, and local compaction (ADR-0030, ADR-0032), memory notes, entry CRUD with approval and archive, settings, and a recall preview, read-only conversation and task-run context previews with the recall trace (ADR-0036), prompt snapshot listing for a run and for the audit view, a verified detail read, and workspace snapshot settings with an immediate purge (ADR-0037), channel turns (`reply_to_mentions`), agent conversation provisioning (`ensure_agent_channels`), agent profile updates (`update_agent`), run-group task listing, a `cancel_turn(turn_id)` that stops a live conversation, group, or task turn and keeps its partial text (ADR-0041), local-only worktree request/prepare/get/list/diff/discard/reconcile operations (ADR-0031), template, agent, task/assignment/approval, history (runs, tool calls, assignment events, audit), and event-stream operations without leaking store or service types. `RemoteClient` also rebuilds itself from a stored token (`resume` over `/api/v1/me`), lists the account's workspaces for a picker (`account_workspaces`), and retries its event socket with backoff, publishing `StreamResumed` after a recovery and stopping with a notice when the server rejects the session (ADR-0053). Both constructors read `/health` first and refuse a server that speaks another API version, naming both numbers, and plain reads retry a connection failure, timeout, `5xx`, or `429` up to three times while writes are sent once (ADR-0054).
- **`crates/cowbot-package`**: `.cowpkg` workspace packages (ADR-0004): ZIP container with a manifest, per-file SHA-256 checksums, export of a workspace, and verified import that always creates a new workspace. Packages carry notes, memory entries, and memory settings; export redacts credentials, and import re-keys and normalizes unknown memory states (ADR-0033). Integrations are deliberately absent from a package: a bot token and a dedupe history are deployment state (ADR-0056).
- **`crates/cowbot-integrations`**: The shared layer every IM adapter sits on (ADR-0056). An `Integration` trait carries only what a platform forces — `run` (its inbound loop) and `deliver` (one outbound post) — and a `Registry` holds one factory per kind, so a platform crate registers itself and the supervisor never learns its name. The rules that cost money when wrong live here and are tested against a fake adapter: `inbound::ingest` claims the platform event id with `INSERT … ON CONFLICT DO NOTHING` *before* posting (a retry is a no-op, and a failed post releases the claim), drops a message from any bot (two bots mentioning each other is an unbounded loop), resolves the author to a CowBot user (`principal::resolve_principal` derives `bridge:{platform}:{integration}:{external}` so two concurrent messages create one row, and leaves the row with no password hash so it cannot sign in), and turns a platform mention of the bound bot into `@AgentName` because only the bot has a CowBot name. `outbound` mirrors only `Sender::Agent` back and chunks long answers on paragraph, line, and sentence boundaries, by *character* count or — through `ChunkLimit::Units` — by UTF-16 code units, which is what a platform measuring its limit that way needs. `supervisor` runs an adapter's inbound loop on one task and its bus-fed mirror on another, so a reconnect does not delay delivery and a slow post does not stall the next message. Four additive tables (`0021`) hold integrations, bindings, principals, and dedupe rows; none is exported in a package, configuration is reachable only through `Store::integration_config`, and `IntegrationRecord` has no configuration field at all. An owner or admin configures one through `crates/cowbot-server/src/integrations.rs` (`GET/POST /workspaces/{ws}/integrations`, `DELETE .../{id}`, `GET/POST .../{id}/bindings`, `DELETE .../{id}/bindings/{external}`): reading is a Member action, writing is administer, the configuration crosses into the server once and is never returned, and a binding resolves both its channel and a named agent inside the workspace so it cannot post into another team's channel. `crate::adapters::registry()` is the process-wide adapter registry startup and the `supported` flag both read. The desktop's Settings → Integrations panel drives all of it. `outbound` chunks by *characters* for a platform that counts characters and by *UTF-16 units* for one that counts units (Telegram), and `label_chunk` is shared so one answer is numbered the same way on every platform. `notice::report_binding_health` asks an adapter about every binding and posts a notice into the CowBot channel of each one that cannot receive, once, for every platform. Two platform adapters exist — `crates/cowbot-mattermost` (ADR-0057) and `crates/cowbot-telegram` (ADR-0058) — so those two rows report `supported: true` and Slack and Feishu stay `false`.
- **`crates/cowbot-service`**: Application services for the local runtime: idempotent local owner/workspace bootstrap, channel/message operations that persist first and then publish events, channel name validation and management with rename, pin, delete, and clear history (ADR-0026), idempotent agent direct-conversation provisioning (ADR-0024), agent profile updates that keep conversations in sync (ADR-0028), channel turns that turn mentions or direct messages into assignment-backed answers with CowBot/OPC context (ADR-0022, ADR-0028), single-agent conversation sessions with independent append-only context branches, projection, compaction, clearing, and channel-attributed usage (ADR-0030, ADR-0034), group conversation creation, participant-scoped mention and default-responder routing, an opt-in model router with documented fallbacks, per-participant branches with peer mirroring, observed reply posting, turn-row persistence, and post-routing capacity skips (ADR-0032), memory and notes with scoped recall, prompt injection for conversation and task turns, the scoped `remember` tool, opt-in extraction with pending review, and package-safe redaction (ADR-0033), the assignment runtime (tree lifecycle, event log, budgets, stall guard, restart reconciliation), the assignment scheduler with wake/re-entry, cross-root concurrency, prepared conversation requests, and run-bound usage recording (ADR-0019, ADR-0029, ADR-0030), the worktree service that requests, prepares, inspects, discards, and reconciles per-task git worktrees and publishes `WorktreeUpdated` (ADR-0031), the approval service (risk policy, workspace allow / ask / deny rules, session decisions, the Bypass Critical tri-state, pending approvals, source-attributed audit), a scheduler-backed crew runner, and the shared `TurnRunner` that opens every turn, publishes its lifecycle events, stores the reply before the terminal event, and keeps a stopped turn's partial text with a stopped marker, with an idempotent `cancel_turn` covering conversation, group, and task turns (ADR-0041), and template management with built-in templates, validation, CRUD, and `.cowtemplate` import/export. Conversation projection, group capacity checks, compaction splits, and router history budgets count tokens with the conversation model's counter (ADR-0035). `PreviewService` rebuilds a conversation participant's next request and a task run's first request as a read-only `PromptPlan` with named prompt slots, ordered messages, tool schemas, and the memory recall trace; it never writes a context entry or a recall statistic (ADR-0036). `PromptSnapshotService` seals and stores the request behind every agent, router, compaction, and memory-extraction call, reads it back with hash verification, and sweeps expired rows on workspace open, settings change, and demand (ADR-0037).
- **`crates/cowbot-cli`**: The `cowbot` binary. `init` opens the local database through `cowbot-client` and prints the session; `run` executes the Planner/Coder/Reviewer crew through `LocalClient::run_crew_with_options` with persisted history, `--db`, `--dry-run`, `--channel`, `--concurrency`, and an interactive `--approval` policy; `channel` and `message` list/create channels and list/post messages (`message post --wait` lets mentioned agents answer; on a group conversation it prints the route source and per-agent reply, failure, and skip counts); `memory` lists, adds, and archives memory entries; `tools` inspects the registry and smoke-tests the sandbox. Settings resolve from `--config`/`COWBOT_CONFIG`/`cowbot.toml` with CLI and environment values taking precedence, and API keys stay in environment variables (ADR-0020).
- **`crates/cowbot-server`**: The self-hosted team-mode server (Phase 2 milestone 2.1, ADR-0043). Opens the same SQLite database through `cowbot-store` and serves an HTTP API with `axum`: `GET /health` with the API version, `POST /api/v1/auth/sign-in`, `POST /api/v1/auth/sign-out`, `POST /api/v1/auth/password`, and `GET /api/v1/me`. Passwords are hashed with Argon2id and refused below ten characters; sign-in spends the same work on an unknown email as on a real one and returns the same error, so accounts cannot be enumerated; sessions are 256-bit opaque bearer tokens stored only as a SHA-256 hash with a two-week default expiry, and a password change drops every session. Failed sign-ins are counted per `X-Forwarded-For` source and refused after ten in fifteen minutes. `AuthenticatedUser` is a `FromRequestParts` extractor, so a handler's signature says whether it needs an identity. Every failure is one JSON `{code, message}` body with a matching status, and a storage error is reported generically while its detail is logged. On an empty database the binary creates the owner and workspace and prints the generated password once. `ServerConfig::from_env` reads eight deployment variables plus `COWBOT_SERVER_WORKSPACE_DIR` and the four all-or-nothing `COWBOT_SERVER_LLM_*` ones, and exits on a value that does not parse rather than falling back; unset values keep the development defaults. `deploy/` holds a multi-stage Dockerfile (unprivileged user, health check on `/health`, one `/data` volume) and a Compose file with Caddy terminating TLS in front of a loopback-bound server, which is also what makes `X-Forwarded-For` trustworthy for the sign-in limiter. The operations guide is `docs/SERVER.md` (ADR-0046). Also serves the workspace surface: list and create workspaces, list/update/remove members, create/list/revoke/accept single-use invitations, and rename a workspace. `require_member` resolves the caller's role before any read or write, a non-member gets `404` rather than `403` so workspace existence cannot be probed, and `Role` in `cowbot-core` carries the policy — `can_manage` (an Admin manages Members but not peers or Owners), `can_grant` (nobody grants a role stronger than their own, and only an Owner grants Owner), `can_invite`, `can_administer`, and `can_write` — with the last Owner protected by a store-level owner count (ADR-0044). Membership changes append audit events sourced `human`. Also serves the collaboration surface — channels and messages, tasks, assignments, runs, tool calls, approvals, permission rules, the workspace policy, agents, audit, and API tokens — with every route resolving the channel or task's workspace and the caller's role first (ADR-0045). The sender of a message is always the authenticated user. `GET /api/v1/workspaces/{id}/stream` is a WebSocket that filters the process-wide bus to the workspace's channels and tasks and sends `{"type":"Resync"}` when a subscriber falls behind. `RemoteClient` in `cowbot-client` implements the same `Client` trait over HTTP and the socket, so the desktop runs against a server; only the members that need the machine it runs on report server mode plainly (worktrees, in-process crew execution, live-turn cancellation, process-local session decisions). Milestone 2.5 also serves the workspace data surfaces — memory notes, entries, settings and recall; conversation creation, settings, context meters, turns, and clearing; the two read-only context previews; prompt snapshots with their settings and purge; workspace-scoped templates (migration `0019`); and `.cowpkg` import and export — and scopes prompt-snapshot reads to their workspace, since a raw snapshot is the most sensitive row in the database (ADR-0047). It also answers channel turns itself when a provider is configured: `TurnExecutor` holds one `ChannelAgentService` per workspace (the service owns the open-turn registry and the compaction branch locks, so a per-request instance would break both), runs `post_message`'s turn in the background after the reply is stored, and reaches clients through the existing `MessagePosted` event. Its tool set is deliberately narrow — `execute_code`, `read_file`, and `write_file`, rooted at `COWBOT_SERVER_WORKSPACE_DIR` — because the desktop's workspace tools assume a local project folder a server does not have. It computes the per-participant context window from two optional `COWBOT_SERVER_LLM_CONTEXT_WINDOW`/`_MAX_OUTPUT_TOKENS` variables, since the server has no model catalogue of its own (ADR-0055).

## Website

`site/` holds the GitHub Pages landing page (plain HTML/CSS/JS, no build step): a hero with an interactive approval demo, platform download links resolved from the GitHub Releases API, feature and architecture sections, and a quick start. It is published from the `gh-pages` branch, which holds an assembled copy of `site/` plus `assets/brand/` and `docs/assets/` so relative asset paths resolve. The `gh-pages` branch is generated output; edit `site/` and republish it with `bash site/publish.sh` (add `--dry-run` to write to `tmp/gh-pages/` without pushing). Pages serves that branch's root.

## Common Development Commands

### Building
```bash
cargo build --workspace
cargo build --release --workspace
```

### Running the CLI
```bash
cargo run -p cowbot-cli -- --help
cargo run -p cowbot-cli -- tools
cargo run -p cowbot-cli -- init --db cowbot.db
cargo run -p cowbot-cli -- run --task "Analyze and write code" --dry-run
```

### Running the Desktop App
```bash
cd desktop
pnpm install
pnpm run tauri dev        # dev window + Vite server
pnpm run build            # type-check and bundle the frontend
pnpm run tauri build -- --no-sign   # local bundles without updater signatures
cargo clippy --manifest-path src-tauri/Cargo.toml --all-targets -- -D warnings
```

`pnpm run tauri build` without `--no-sign` needs the updater signing key; CI supplies it from repository secrets. See `desktop/README.md`.

### Testing
```bash
# Run all workspace tests
cargo test --workspace

# Run tests for a specific crate
cargo test -p cowbot-core
cargo test -p cowbot-bus
cargo test -p cowbot-tools

# Run a single specific test
cargo test -p cowbot-bus -- test_bus_publish_and_receive --exact
```

### Linting & Formatting
```bash
cargo clippy --workspace --all-targets -- -D warnings
cargo fmt --check
cargo fmt
```
